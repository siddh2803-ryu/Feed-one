# Feed One: Decisions Register

All decisions carry status labels per PRD Section 0.1. Decisions marked **[PROPOSED]** serve as the working baseline until explicitly confirmed or amended by the team.

| ID | Topic | Status | Decision Summary | PRD / Ref Section |
|---|---|---|---|---|
| **D1** | Split Donations | [PROPOSED] | Out of scope for MVP. One recipient must be able to accept the full quantity. Multi-recipient allocation is planned for later phases. | Ref §2.4, PRD §4 |
| **D2** | Transport & Food Movement | [PROPOSED] | Recipient (or its volunteer) collects from donor. No donor drop-off or third-party courier logistics in MVP. | Ref §2.4, PRD §4 |
| **D3** | Unknown Constraints & Grouping | [PROPOSED] | Constraints return `pass`, `fail`, or `unknown`. Any `fail` excludes. All `pass` = **Eligible**. Any `unknown` without `fail` = **Needs confirmation** (ranked after Eligible). Safety (C5) `unknown` counts as `fail`. | Ref §2.4, PRD §4, §7.3 |
| **D4** | Measurement Units | [PROPOSED] | Exactly one unit per donation (`items` or `kg`). Recipient capacity is compared only against the same unit; mismatch or missing = `unknown` (`C2_UNIT_MISMATCH`). No runtime unit conversions. | Ref §2.4, PRD §4 |
| **D5** | TinyFish Discovery Role | [PROPOSED] | Background directory enrichment only, supervised by coordinator. Never executed inside per-donation matching requests. Discovered records are stored as **Leads** with `public_source` provenance and can never be `Eligible`. | Ref §2.4, PRD §4, §11 |
| **D6** | Distance Calculation | [PROPOSED] | Straight-line (Haversine) distance in km from stored coordinates, visibly labeled "approx. distance". No travel-time or routing claims. No geocoding API in MVP. | Ref §2.4, PRD §4 |
| **D7** | Confirmation Workflow | [PROPOSED] | Sequential offers: donor selects one candidate, an offer is dispatched with a respond-by deadline. Recipient explicitly accepts or declines. Decline or expiry returns donation to remaining candidates. | Ref §2.4, PRD §4, §7.2 |
| **D8** | Offer Response Window | [PROPOSED] | `respond_by = min(sent_at + OFFER_RESPONSE_MINUTES, pickup_deadline - OFFER_DEADLINE_BUFFER_MINUTES)`, with defaults 15m and 30m. | Ref §2.4, PRD §4, §7.2 |
| **D9** | Event Actors | [PROPOSED] | `Collected` recorded by donor or recipient. `Delivered` recorded by recipient only. Every lifecycle event immutably stores actor role, ID, and timestamps. | Ref §2.4, PRD §4, §7.1 |
| **D10** | Food Safety Screening | [PROPOSED] | Donor attests storage category, packaged/sealed, prepared time, use-by time, and allergen notes. Evaluated by pure deterministic rule table routing to `eligible_by_rules`, `blocked`, or `needs_review`. System never outputs "safe". Final verification occurs at physical handoff. | Ref §2.4, PRD §4, §7.4 |
| **D11** | Accounts & Personas | [PROPOSED] | Seeded demo accounts with visible top-bar role switcher and one-click persona login. All demo entities flagged `is_demo = true`. No public self-registration in MVP. | Ref §2.4, PRD §4, §5 |
| **D12** | Timezone Handling | [PROPOSED] | All timestamps stored in UTC ISO 8601. Displayed in UI according to configured region timezone (`REGION_TIMEZONE`). | Ref §2.4, PRD §4 |
| **D13** | Offer Eligibility Scope | [PROPOSED] | P0 offers sent to `Eligible` candidates only. P1 allows offers to onboarded `Needs confirmation` candidates with explicit donor acknowledgement of unknowns. Leads never receive in-app offers. | PRD §3 (G1), §4 |
| **D14** | Availability Model | [PROPOSED] | Recipients declare weekly recurring collection windows (day of week, start, end). Published opening hours are stored separately with `public_source` provenance and can never satisfy C3. | PRD §3 (G2), §4 |
| **D15** | Timers & Expiry Architecture | [PROPOSED] | Matching runs synchronously; "Matching in Progress" is an ephemeral UI state. Offer and pickup expiries are applied via idempotent background job `applyExpiries(now)` every minute, plus lazy scoped evaluation on every read/write. | PRD §3 (G6), §4, §12.6 |
| **D16** | Donation Editing | [PROPOSED] | Editable only in `listed`, `match_recommended`, `no_match`. Matching-relevant field edits invalidate candidate cache, clear coordinator safety approvals, and re-run safety & matching. Locked once offer is sent. | PRD §3 (G7), §4 |
| **D17** | Safety Starter Rules | [PROPOSED] | Conservative starter table (rules S1 to S8). Amber/review path for temperature-controlled, unpackaged, or non-dated items. Marked visibly: *"Pending review by a qualified food-safety person"*. | PRD §3 (G8), §4, §7.4 |
| **D18** | Food Categories | [PROPOSED] | Standard enum: `bakery`, `produce`, `packaged_dry`, `cooked_meals`, `dairy_eggs`, `beverages`, `other`. Managed via configuration table. | PRD §3 (G8), §4 |
| **D19** | Expiry Grace & Operational Correction | [PROPOSED] | Pickup expiry triggers at `pickup_deadline + EXPIRY_GRACE_MINUTES` (default 15m). Coordinator may correct `pickup_expired` to `collected` within 24h with mandatory operational reason; recorded as an explicit event, not an overwrite. | PRD §3 (G9), §4 |
| **D20** | In-App Notifications | [PROPOSED] | In-app notifications only: unread badge counter, notification stream, and polling/realtime refresh. External SMS, push, or email out of scope for MVP. | PRD §3 (G10), §4 |
| **D21** | Region Configuration | [PROPOSED] | Pilot region coordinates (`REGION_CENTER_LAT`, `REGION_CENTER_LNG`) and timezone (`REGION_TIMEZONE`) injected via environment variables. Demo seed entities positioned using deterministic km offsets. | PRD §3 (G11), §4 |
| **D22** | Concurrency & Offer Locking | [PROPOSED] | Strictly one pending (`sent`) offer per donation at any time, enforced by partial unique database index. Optimistic locking on transitions via version column. | PRD §3 (G12), §4, §13.2 |
| **D23** | Lead Conversion Lifecycle | [PROPOSED] | Lead promoted to Onboarded only by coordinator after out-of-band verification. Verified attributes receive `coordinator_verified` provenance. Leads never auto-promoted. | PRD §3 (G13), §4 |
| **D24** | Provenance Levels | [PROPOSED] | Provenance hierarchy: `recipient_confirmed`, `coordinator_verified`, `seeded_demo`, `public_source`, `system_derived`. C1 to C4 can only pass with non-public provenance; `public_source` yields `unknown`. | PRD §3 (G14), §4, §7.6 |
| **D25** | Matching Triggers | [PROPOSED] | Matching triggered explicitly on listing submission, offer decline/expiry/withdrawal, matching-relevant edit, safety review decision, and manual "Re-check" button. Every run is stored with a snapshot. | PRD §3 (G15), §4 |
| **D26** | Privacy & Contact Disclosure | [PROPOSED] | Before offer acceptance, recipient sees only donor display name, general locality, approximate distance, and food specifications. Exact pickup address and direct phone are disclosed only upon mutual acceptance. | PRD §3 (G16), §4 |
| **D27** | LLM Role & Boundaries | [PROPOSED] | MVP explanations generated from deterministic templates. LLM features (`LLM_EXPLANATIONS`, `LLM_EXTRACTION`) disabled by default behind feature flags. LLM never decides eligibility, ranking, safety, or lifecycle. | PRD §3 (G17), §4, §10.6 |
| **D28** | Technology Stack | [PROPOSED] | Next.js 15 (App Router) + TypeScript (strict) + Tailwind CSS + shadcn/ui (Radix primitives); Supabase Postgres + Drizzle ORM; Vitest for unit tests; Playwright for E2E. | PRD §3 (G18), §4, §12.1 |
| **D29** | Pickup Window Algorithm (C3) | [PROPOSED] | Effective window $W = [\max(\text{available\_from}, \text{now}), \text{pickup\_deadline}]$. Intersected with recipient's collection windows on relevant dates. C3 passes if at least one slot has duration $\ge \text{MIN\_PICKUP\_SLOT\_MINUTES}$ (30m). | PRD §3 (G3), §4, §7.3 |
| **D30** | Category & Capacity Semantics | [PROPOSED] | `accepted_categories` is nullable and exhaustive when set. Capacities stored as `capacity_items` (integer) and `capacity_kg` (numeric). Service area is center coordinate + radius in km. | PRD §3 (G4, G5), §4, §7.3 |
| **D31** | Late Offer Guard | [PROPOSED] | If $\text{respond\_by} - \text{now} < \text{MIN\_RESPONSE\_MINUTES}$ (5m), sending an offer is prohibited with clear user guidance ("Too close to deadline"). | PRD §3 (G19), §4 |
